# Розгортання Parket Planet: Vercel + Render

```
https://<проєкт>.vercel.app        ← фронтенд (статична збірка React)
        │  fetch(REACT_APP_API_URL + '/api/...')
        ▼
https://<сервіс>.onrender.com      ← бекенд FastAPI
        │
        ▼
Postgres                            ← товари, категорії, замовлення, фото
```

Порядок важливий: **спочатку бекенд**, бо його адреса потрібна фронтенду.

---

## Крок 1. Залити проєкт на GitHub

Заливається весь репозиторій — і `src/`, і `backend/`. Один репозиторій
обслуговує обидва хостинги: Vercel бере з нього фронтенд, Render — теку
`backend/`.

```bash
git add -A
git commit -m "Динамічні категорії, преміальні кнопки, intro-анімація"
git push origin main
```

Що **не** потрапляє в git і так і має бути (див. `.gitignore` та
`backend/.gitignore`):

| Файл | Чому |
|---|---|
| `backend/parket_planet.db` | локальна база розробника |
| `backend/.secret` | ключ підпису сесій |
| `backend/uploads/` | старі локальні фото |
| `build/` | Vercel збирає сам |
| `node_modules/` | ставляться при збірці |

Паролів і ключів у репозиторії немає: усі секрети задаються змінними
оточення на хостингу (`sync: false` у `render.yaml`).

---

## Крок 2. База даних (Postgres)

Безкоштовна SQLite на Render не годиться: диск там ефемерний, і після
кожного передеплою чи засинання сервісу товари, замовлення та завантажені
фото зникли б.

Найпростіше — **Render → New → Postgres** (free). Або Neon / Supabase.
Після створення скопіюйте **Internal Database URL** (для сервісу в тому ж
Render) або **External Database URL** (для іншого провайдера) — рядок виду:

```
postgresql://user:pass@host/dbname
```

Драйвер і формат URL код нормалізує сам (`backend/app/config.py`), тому
`postgres://…` теж підійде.

## Крок 3. Бекенд на Render

1. **New → Blueprint** → вибрати цей репозиторій. Render прочитає
   `render.yaml` у корені й запропонує створити сервіс `parket-planet-api`.
2. Заповнити змінні, які Render спитає (вони позначені `sync: false`):

| Змінна | Значення | Навіщо |
|---|---|---|
| `PP_DATABASE_URL` | рядок із Кроку 2 | без неї дані не переживуть передеплой |
| `PP_ALLOWED_ORIGINS` | `https://<проєкт>.vercel.app` | CORS; **без слеша в кінці** |
| `PP_ADMIN_PASSWORD` | ваш початковий пароль | діє до першої зміни в адмінці |
| `NOVA_POSHTA_API_KEY` | ключ Нової пошти | лишається тільки на сервері |

Виставляються автоматично з `render.yaml`:

| Змінна | Значення | Навіщо |
|---|---|---|
| `PP_SECRET_KEY` | генерується Render | підпис сесійного токена |
| `PP_COOKIE_SAMESITE` | `none` | фронтенд і бекенд на різних доменах |
| `PP_COOKIE_SECURE` | `1` | без цього браузер не збереже куку по HTTPS |

`PORT` підставляє сама платформа — у команді запуску стоїть `$PORT`,
нічого прошивати не треба.

3. Дочекатися деплою → скопіювати адресу виду
   `https://parket-planet-api.onrender.com`.
4. Перевірити: `https://parket-planet-api.onrender.com/api/health` має
   віддати `{"status":"ok"}`, а `/api/categories` — список категорій.

> **Про безкоштовний тариф.** Сервіс засинає після ~15 хвилин без запитів,
> і перший запит після сну триває 30–60 секунд. Сайт це переживає: поки
> бекенд прокидається, каталог показує статичний фолбек, а не помилку.
> Якщо потрібна миттєва відповідь — платний план Render.

---

## Крок 4. Фронтенд на Vercel

1. **Add New → Project** → імпортувати той самий репозиторій.
2. Framework Preset: **Other** (усе потрібне вже є у `vercel.json`:
   команда збірки, тека `build`, SPA-переписування).
3. **Environment Variables** → додати для Production:

| Змінна | Значення |
|---|---|
| `REACT_APP_API_URL` | `https://parket-planet-api.onrender.com` |

   Без слеша в кінці. CRA вшиває цю змінну **під час збірки**, тому після
   її зміни потрібен новий деплой (Deployments → Redeploy).

4. **Deploy** → отримати адресу виду `https://parket-planet.vercel.app`.

---

## Крок 5. Замкнути коло

Поверніться в Render → сервіс → **Environment** і впишіть отриману адресу
Vercel у `PP_ALLOWED_ORIGINS`, якщо на Кроці 3 її ще не було. Render
перезапустить сервіс сам.

Без цього браузер заблокує запити з фронтенда: у відповіді не буде
заголовка `Access-Control-Allow-Origin`.

---

## Крок 6. Перевірка після деплою

| Що перевірити | Як |
|---|---|
| Каталог живий | головна показує категорії з бази, а не 4 статичні |
| Категорії | клік по картці відкриває товари, адреса `/<slug>` |
| Оновлення сторінки | F5 на `/parquet` не дає 404 (працює SPA-rewrite) |
| Товар | `/product/<slug>` відкривається напряму |
| Адмінка | `/admin` → вхід → зміна товару видно на сайті |
| Фото | завантажене в адмінці фото показується на сайті |
| Нова пошта | на `/checkout` вантажаться області й відділення |

## Відомі особливості

**Кука адмінки — крос-сайтова.** `vercel.app` і `onrender.com` — різні
сайти, тому сесія адміністратора їде в куці `SameSite=None; Secure`.
Safari та браузери з увімкненим блокуванням сторонніх кук можуть її не
зберегти — тоді вхід в адмінку не спрацює саме в такому браузері
(публічна частина сайту працює завжди). Два надійні рішення:

* прив'язати власний домен до обох сервісів (`site.com` і `api.site.com`) —
  тоді кука стає first-party;
* або розгорнути все на Vercel одним доменом — див. `DEPLOY-VERCEL.md`.

**Прев'ю-деплої Vercel.** У кожного прев'ю своя адреса, і вона не
збігається з `PP_ALLOWED_ORIGINS`, тому адмінка на прев'ю не працюватиме.
Це очікувано; за потреби додайте адресу прев'ю в CORS через кому.

**Секрети.** Ключ Нової пошти, пароль адміністратора й рядок підключення
до бази існують ЛИШЕ як змінні оточення Render. У фронтенд-бандл вони не
потрапляють: браузер ходить у Нову пошту через `/api/delivery/*`, а не
напряму. Перевірити можна так:

```bash
npm run build
grep -ri "localhost\|NOVA_POSHTA\|PP_ADMIN" build/static/js/   # має бути порожньо
```
